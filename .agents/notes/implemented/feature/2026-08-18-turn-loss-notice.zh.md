# Agent Note: 回合丢失通知——告知模型失败回合的流式答案未被保留

Status: implemented

[English](2026-08-18-turn-loss-notice.md) | 中文

## Problem

中途出错的回合会提交 `turn/end {kind:'error'}` 及其 `assistant/chunk` 轨迹,但不会提交 `assistant/message`——surface 投影仅从产生消息的事件派生模型历史,因此模型的下一次请求会从用户的问题直接跳到其下一条提示。而与此同时,用户看着部分答案流式输出。这一不对称在生产使用中显现(2026-08-18):用户询问"你审查过的那通电话";模型没有任何审查记录,诚实地重新推导,选了另一通电话。若不修复,失败模式比重新推导更糟:被问及"如你之前所说"时,带着无声空洞的模型要么虚构一个貌似合理的先前陈述,要么自相矛盾,且两者都显得笃定。

## Decision

一个无配置的上下文插件(`@deepseek-ai/dsh-turn-loss-notice`)在下一回合的第一个进入步骤派生丢失事实,并前置一条由生产者包装的 `<system-reminder>` 用户消息:上一次回复中途失败且未被保留。谓词——日志中最近的 `turn/end` 为 `{kind:'error'}` 且该回合存在晚于其最后一条含内容 `assistant/message` 的 `text-delta` 块——只读会话日志,因此机制无状态、对重启免疫,且连续失败的重试恰在发生新丢失时才再次触发。投递通过 `agent/pre-step` 前置完成,循环在模型调用前将其作为注入的 `user/message` 提交:即使承载回合同样失败也已持久记录,并且在日志与请求中都先于用户的提示。触发语义与模型可见文本钉在包 README 的 Model Experience 一节。

## Alternatives considered

- **在出错时刻由 `session/event` 监听器追加通知**(设计的 r1)。已否决:它必须处理追加期间再追加的重入问题,需要为连续失败设计专门的去重规则,并且会写下一条可能永远无人读到的通知(对话就此结束的情形)。pre-step 派生保留了 r1 的持久性——决策消息在模型调用前提交——并增加了无状态性。
- **自动提交部分回合。** 已否决:半成品答案一旦成为已提交历史,会诱使模型在未经验证的片段上继续构建;空白会发问,有损记录会断言。
- **在恢复缺失时用数据库重建上下文。** 已否决:重建的上下文不含工具结果,模型将看到自己过去的断言却没有底层数据——重放式虚构。
- **用任意块而非 `text-delta` 触发。** 依实测否决:真实块流量约三分之一是工具调用结构,且回合经常以工具调用块开头——在任何文字之前出错是常见时机,必须保持静默(用户什么也没看到)。

## Consequences

代价:每次实际丢失一条约 70 token 的保留上下文消息,以及每回合第一个进入步骤的一次全日志扫描(以会话长度为界;与 agent-instructions 已使用的全扫描模式相同)。收益:"如你之前所说"现在得到"我没有那条记录,让我重新做"而非虚构,并且这种诚实的不对称——用户可能看到了模型无法记住的内容——被告知给了唯一无法自行得知的一方。崩溃路径(完全没有 `turn/end`)在构造上仍未覆盖;该领域属于会话修复的合成收尾事件,已记录于包 README,以免谓词被扩展到它无法匹配的形态。

## Testing

十一个行为测试通过脚本化适配器驱动真实的 agent 循环:正向丢失形态(通知内容、来源、在日志与请求中先于提示的顺序),负向形态(完成的回合、流式输出前出错、仅推理丢失、仅工具调用增量丢失、已提交尾部的多步骤出错、带未提交文本的用户中止),多步骤丢失尾部正向形态,跨回合锚定(早先回合的提交不掩盖出错回合的丢失),以及连续失败的再触发。中止与工具调用增量两个负向测试由变异推导而来:各自是其合取项被删除时唯一失败的测试。
