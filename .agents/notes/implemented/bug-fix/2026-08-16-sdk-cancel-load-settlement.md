# Agent Note: Replay a load's operation queue at settlement

Status: implemented

English | [中文](2026-08-16-sdk-cancel-load-settlement.zh.md)

## Problem

`session/cancel` must abort exactly the prompts the client sent before it — on a live session, wire order does this for free, but while a lazy create or resume is in flight, prompts and cancels pile up against a session that does not exist yet. [`session/cancel`](../feature/2026-08-15-sdk-session-cancel.md) and [`session/resume`](../feature/2026-08-15-sdk-session-resume.md) first modelled this with cancellation state beside the load: a session-keyed marker, then a waiter count, then a count snapshotted at cancel arrival. Four successive review panels each found the current model's ordering broken in a new place: the marker was dropped by a failing resume and leaked past a succeeding one; the boolean applied the abort at the first waiter's settlement, before a second waiter enqueued; the live count deferred the abort past a prompt sent after the cancel, which was acknowledged and then silently discarded; the snapshot fixed who was counted but not who decremented, so a cancel that covered nobody was inherited into a successor create and killed a post-cancel prompt, and a covered prompt reaching that successor through the failed resume's rejection continuation travelled a deeper promise chain than a direct joiner, enqueued second, and escaped the abort that was meant for it.

The constant underneath: the agent must observe followups and cancels in the order the client's prompts and cancels arrived on the wire, and every scalar model reconstructed that order from counts plus an assumption about promise-continuation ordering. The assumption was false — reaction-registration order is not settlement order when reactions sit at different chain depths — and no count can recover an order it never stored.

## Decision

A pending load owns an ordered operation queue. Each `session/prompt` and `session/cancel` handler appends synchronously in its own RPC turn, so the queue's order is the wire's order by construction. The load's own settlement continuation — registered when the load starts, and therefore the first reaction on it — replays the queue against the live agent in one pass: `followup` for prompts, `agent.cancel({ kind: 'user' })` for cancels. Delivery happens in one continuation, so no joiner's chain depth can reorder it, and each cancel lands exactly between the messages that preceded it and those that followed.

A queued prompt's RPC resolves with its pre-minted `messageId` after replay, and rejects when the load fails; it reads the load's `outcome`, which follows the handoff, while `session/resume` reads the attempt's own `task`. A queued cancel carries its own settlement on the op object, so its RPC resolves `{}` at the moment that cancel's fate is decided — after its abort ran in a replay, at the transfer that drops it as a leading cancel, or when a dead load or a refused replay drops the queue — and never waits out a successor it was dropped from. The op transfers by reference, so a surviving cancel's settlement rides into the successor with it. The record itself carries no cancellation state.

When a resume fails, the queue is handed to the lazy create that continues it, minus leading cancels: a cancel with no prompt ahead of it has nothing in the successor to sweep — the successor's only content postdates it — so it dies with the failed load. A failed create hands over nothing; its queued prompts reject with the create's error. During shutdown no successor is started, and the queued prompts reject with the resume's error.

The registry validation (`ctx.agents.get` identity check) runs once per replay rather than once per prompt: the replay is one continuation, and the registry cannot change between its statements. A stale record rejects every queued prompt with the same disposed-agent error the live path throws.

## Alternatives considered

**Session-keyed marker, waiter boolean, live waiter count, count snapshotted at cancel arrival.** Each shipped, in that order, and each was rejected by the next review round with a reproduced ordering violation (runs `panel-dsh-wiring-r2-*`, `panel-dsh-cancel-r3-*`, `-r4-*`, `-r5-*`). The terminal defect class was structural, not a tuning error: coverage — which prompts a cancel owns — is positional information, and a scalar stores only cardinality, so every variant leaned on promise-continuation order to reconstruct position and broke wherever that order diverged from wire order.

**Per-prompt coverage flags instead of a queue.** Tag each prompt covered/uncovered at join time; only covered prompts hold the abort back. Rejected: correct for one cancel, but coverage is relative to the latest cancel — `prompt, cancel, prompt, cancel` needs per-prompt generations to say which cancel owns which prompt, at which point the flags-plus-generations reconstruct exactly the ordered queue, stored worse.

**Keep cancels out of the queue and apply at most one abort per load.** Rejected: the wire can interleave `prompt, cancel, prompt, cancel, prompt`, and each cancel is an instruction to abort what preceded it. Replaying the queue honours that for any number of cancels; a single coalesced abort cannot.

**Transfer the whole queue, leading cancels included, on resume failure.** Rejected: an abort delivered to a fresh agent ahead of every message would be a no-op at best, and its only observable effects would touch work the cancel postdates. Dropping only leading cancels keeps every cancel that still has queued messages to sweep.

**Guard the window between record publication and settlement.** `createSession` publishes into `sessions` before its task settles, so `session/cancel` could in principle take the live path mid-load. Consulting the pending map before the record map in `prompt`, `cancel`, and `resume` closes this structurally; the window was also shown unreachable from `handleRequest` or the wire — every hop from publication to replay is a microtask, and a transport-delivered frame is a macrotask.

## Consequences

**Bought**: one mechanism replaces three interacting scalars, their clamp, and the inheritance argument. Wire order is stored once, at arrival, and replayed verbatim; nothing downstream reasons about continuation depth. Interleaved multi-cancel sequences replay faithfully, which no counting variant did. A loading session and a live session answer the same wire order with the same abort placement.

**Paid**: a queued prompt's `followup` runs in the load's settlement continuation rather than its own RPC handler, so its RPC resolves one reaction later than before, and the registry identity check is one decision per replay — a stale record rejects every queued prompt rather than per-prompt, while queued cancels settle `{}` unfailingly. Replay assumes non-throwing delivery: `followup` and `cancel` are inbox operations, and a synchronous event listener that throws through them abandons the rest of the queue and rejects every queued prompt, delivered ones included — reachable only from a host-supplied transport peer or an in-process listener, not from the shipped stdio transport. The `session/resume` RPC reports its own attempt's result while queued prompts follow the successor, so the two read different promises off one load entry; during shutdown, queued prompts on a failing resume reject with that load's own error rather than a shutdown error.

## Testing

Keyless unit, all in `packages/sdk/server/tests/server.spec.ts`. `replays interleaved prompts and cancels on one load in wire order` pins the queue itself. `keeps wire order across a failed resume when a later prompt joins the successor` fails under any model that lets continuation depth reorder delivery. `drops a cancel that covered no prompt with the load it raced` pins the leading-cancel drop. `leaves a prompt that arrives after the cancel out of that cancel` and `out of the successor create` pin abort placement on both load paths. `aborts only after every prompt queued ahead of the cancel on one in-flight create` and the failing-resume variant pin multi-prompt coverage. `does not acknowledge a transferred cancel before the successor runs its abort` and `acknowledges a dropped leading cancel even when the successor never settles` pin a queued cancel's settlement to its own fate: never before its abort ran, and never behind a successor it was dropped from. `does not start a successor create when a resume fails during shutdown` pins teardown containment. `rejects the whole queue on one registry check when the loaded agent is already detached` pins single-decision replay validation, whole-queue rejection, and the cancel RPC staying unfailable. `does not keep a pending cancel after lazy creation fails` keeps a later independent retry unaffected.
